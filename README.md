# StreamVessel log collector

StreamVessel log collector: OTel Collector distribution (issue #1) and Cloudflare Worker (issue #2).

## Log agent (`sv-log-agent`)

An [OpenTelemetry Collector](https://opentelemetry.io/docs/collector/) distribution, built with `ocb`, that tails files or receives OTLP, batches records into gzipped NDJSON and uploads each batch straight into the customer's bucket through a URL that StreamVessel presigns. Log bytes never pass through StreamVessel's servers. Tracking issue: #1, part of streamvessel/sv-be#384.

### Layout

| Path | What |
|---|---|
| `builder-config.yaml` | `ocb` manifest; every component pinned to collector v0.163.0 / v1.69.0 |
| `cmd/sv-log-agent/` | Distribution generated by `ocb` and committed (CI checks it is current); `featuregates.go` is hand-written |
| `exporter/svexporter/` | The one custom component: exporter type `sv` |
| `examples/` | `agent.yaml` (nginx), `compose/`, `kubernetes/` (DaemonSet, sidecar) |
| `packaging/` | systemd unit and environment file |
| `test/e2e/` | Docker Compose stack with a fake sv-be and MiniStack; kill-mid-batch test |

### Pipeline

```
filelog / otlp → memory_limiter → resourcedetection → sv exporter
                                                       └ persistent sending_queue (file_storage)
                                                         → batch of 16 MB uncompressed or 5 min
                                                         → NDJSON + gzip + SHA-256
                                                         → POST /be/ingest/uploads → PUT to bucket
```

There is no batch processor: batching happens in the exporter's queue after the records are on disk, so a crash loses nothing the receivers handed over. `retry_on_failure.max_elapsed_time` is 0, so a batch is retried until it lands. The binary turns on the `stanza.synchronousLogEmitter` feature gate, so filelog does not save a read offset before the records reach the queue.

Authentication is the stock `oauth2client` extension (client credentials grant against `${SV_SERVER}/be/ingest/oauth/token`); the agent has no auth code of its own. The secret is always read from a file (`client_secret_file`), which the extension re-reads, so rotating it needs no restart. Each batch is announced with `POST /be/ingest/uploads {instance, startTs, endTs, sha256}` (contract: streamvessel/sv-be#386). The PUT to the bucket goes through a separate plain HTTP client with no `Authorization` header and exactly the headers sv-be returned.

### NDJSON record

```json
{"timestamp":"2026-10-20T12:00:00.123456Z","level":"warn","status":404,"message":"GET /a HTTP/1.1 …","host":"web-1","file":"/var/log/nginx/access.log","attrs":{"method":"GET"}}
```

`timestamp` is RFC 3339 UTC with at most 6 fractional digits (the parsed time, else the observed time), never altered; `level` comes from the severity; `status` appears when a parser extracted one; `attrs` holds the remaining attributes.

The batch's `startTs`/`endTs` (which name the object) come from the records' times, each clamped to [read time − 7 days, read time + 1 min]. sv-be refuses a batch for good when `startTs` is over 30 days old or `endTs` over 5 minutes ahead, so one stale line (a re-read rotated file) or one from a host with a bad clock cannot get the batch dropped. The read time is stored with the record, so a retried batch gets the same key.

### Responses

| Response | Agent does |
|---|---|
| `client_secret_file` missing, empty or unreadable | logged at error level; the batch is kept and retried; no offline slot is used (sv-be is not down) |
| token request `invalid_client` | permanent: logged loudly, batch dropped, no retry loop |
| 401 `invalid_token` | logged and retried; succeeds once the extension has a new token (it keeps its cached token until near expiry, so up to about 10 minutes) |
| 403 `agent_revoked` / `scope_changed`, 400 (`invalid_request`, `invalid_instance`) | permanent, logged at error level with `error_description`; on revocation offline slots are discarded |
| 404 `not_found` | ingest is disabled on sv-be: backoff, the batch is kept |
| 409 `too_many_instances` / `connection_unreadable` | logged at error level with `error_description`; the batch is kept and retried after an hour |
| 429 / 5xx (incl. 502 `storage_unavailable`) / no answer | backoff (honours `Retry-After`); uploads to an offline slot if one is held |
| 412 on PUT | already stored (the key carries the hash): success |
| 403 on PUT | up to 3 fresh URLs per attempt, then logged as a signing or clock problem and backed off |
| 400 / 409 / 501 on PUT | provider code logged; 3 retries with backoff, then the batch is held (`hold_interval`, 15 min) until an operator fixes it |

Offline slots: the exporter keeps up to 8 pre-minted upload slots from `POST /be/ingest/leases`, each used once. sv-be counts every slot it minted against that cap until the slot expires, used or not, so the agent asks for more only at startup or once one of its slots has expired, and keeps every slot it gets. The pool is saved in the queue's `file_storage`, so a restart on the same volume keeps its slots; without a volume a restarted agent has none until the old ones expire (up to an hour), and the persistent queue still covers an outage. Saved slots are credentials and their URLs are never logged. After an empty answer (sv-be still counts slots from before a restart) it waits 10–15 minutes; a 429 on leases (6 per minute per agent, shared by its instances) is retried after `Retry-After` plus jitter. `offline_slots.pool_size: 0` turns them off.

A wrong or deleted secret: the oauth2client extension auto-detects how to send the client credentials, so each failed token exchange is two requests. sv-be limits failures to 10 per 5 minutes per client id and source IP, so a bad secret is rate-limited after 5 attempts; fix the secret file and the next attempt after the limit window succeeds.

### Configuration

| Variable | Meaning |
|---|---|
| `SV_SERVER` | `https://app.streamvessel.com`, no trailing slash |
| `SV_CLIENT_ID` | the agent's client id (`sva_…`) |
| `SV_CLIENT_SECRET_FILE` | path to the file holding the secret. Never pass the secret in the environment or on the command line |
| `SV_INSTANCE` | folder name for this host or workload, `[A-Za-z0-9._-]{1,63}`; defaults to the host name. DaemonSet: the node name; sidecar: the workload name; never the pod name |
| `SV_STORAGE_DIR` | read offsets and the persistent queue (default `/var/lib/sv-log-agent`) |

```sh
SV_SERVER=https://app.streamvessel.com SV_CLIENT_ID=sva_… \
SV_CLIENT_SECRET_FILE=/etc/sv-log-agent/secret sv-log-agent --config examples/agent.yaml
```

### Build and test

Requires Go 1.26.10 (the Makefile pins it through `GOTOOLCHAIN`) and Docker for the e2e test.

```sh
make test              # exporter unit tests against an httptest fake of sv-be
make generate          # regenerate cmd/sv-log-agent with ocb v0.163.0
make check-generated   # fail if the committed distribution is stale
make build             # bin/sv-log-agent: static, -trimpath, empty build id (reproducible)
make e2e               # Compose: SIGKILL mid-batch + sv-be outage, every line must arrive
```

Releases (`v*` tags) run goreleaser: static Linux amd64/arm64 archives, deb/rpm packages with the systemd unit, and the image `ghcr.io/streamvessel/sv-log-agent`.

The Compose test runs against `test/e2e/fakesvbe`, a stand-in for sv-be's ingest API that presigns real S3 PUTs against MiniStack, until sv-be (streamvessel/sv-be#385) publishes an image.
